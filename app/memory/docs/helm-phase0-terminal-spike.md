## What Was Done

Built the Phase 0 spike from the planning docs in `Helm/files/`. The spike's job per
`app-plan.md` was to prove the risky parts — SwiftTerm embedded in SwiftUI, a PTY
login shell, programmatic command sending, and cwd sync — before building UI on top.
All of it works, verified in a running app rather than by inspection.

### Repo scaffolding

Created the modular layout from `folder-structure.md`: thin `App/` shell, logic in
local Swift packages (`HelmCore` with zero dependencies, `HelmTerminal` on top of
it), `Docs/adr/`, `Scripts/bootstrap.sh`. `git init` run; nothing committed.

Swift 6 language mode with full strict concurrency, macOS 14 minimum. macOS 14 rather
than the plan's macOS 13 because `@Observable` requires it — and per the release
plan's "support the last two macOS majors", 14 is already generous in 2026.

### Key decisions (both have ADRs in `Docs/adr/`)

**ADR-0005 — generated Xcode project.** `Helm.xcodeproj` is generated by XcodeGen
from `project.yml` and git-ignored, deviating from the folder-structure doc which
lists it as a checked-in file. Rationale: reviewable build settings, no `.pbxproj`
merge conflicts. Trap worth remembering: settings changed in Xcode's UI are silently
lost on the next `xcodegen generate` — `project.yml` is the only source of truth.

**ADR-0003 — shell integration via `ZDOTDIR`.** This is the substantive one. Risk #3
in the plan ("keeping browser and shell cwd in sync is genuinely subtle") is solved
by having the shell report its state via OSC escape sequences:

- OSC 7 on every prompt → working directory, surfaced by SwiftTerm as
  `hostCurrentDirectoryUpdate`.
- OSC 133 semantic marks → command start and exit code.

Hooks are injected by pointing `ZDOTDIR` at Helm-owned zsh shims (`.zshenv`,
`.zprofile`, `.zshrc`) that source the user's real dotfiles and then hand `ZDOTDIR`
back. Chosen over sending `source …` into the PTY because that pollutes scrollback
and shell history. Same approach VS Code uses.

Three non-obvious things this got right, each of which would have been a subtle bug:

1. **The shims reclaim `ZDOTDIR`.** Setting `ZDOTDIR` inside `.zshenv` is a common
   way to relocate zsh config. If a user does that, zsh reads all later startup files
   from *their* directory and Helm's `.zshrc` never runs. Each shim notes where the
   user's value points, then resets `ZDOTDIR` to Helm's via `HELM_ZDOTDIR`.
2. **Hooks are prepended, not appended.** `precmd` hooks run in sequence and each
   one's commands overwrite `$?`. Helm's hook is spliced onto the front of
   `precmd_functions` instead of using `add-zsh-hook`, or the exit code it reports
   would be some other hook's status.
3. **Login shell (`zsh -l`).** A non-login shell skips `/etc/zprofile` and
   `path_helper`, so `PATH` would differ from the real terminal and buttons would
   fail for Homebrew/mise/asdf tools.

### SwiftTerm findings

Read the actual API rather than assuming. Worth knowing for later:

- `LocalProcessTerminalView` provides everything needed: `startProcess(…,
  currentDirectory:)`, OSC 7 via delegate, `terminate()`. Delegate callbacks land on
  the main queue (`LocalProcess` defaults its dispatch queue to `.main`), so
  `MainActor.assumeIsolated` is safe in the delegate conformances.
- **SwiftTerm has no OSC 133 support**, but `terminal.parser.oscHandlers[code]` is
  public and custom handlers are checked *before* the built-ins. `PTYSession`
  registers its own for 133. No fork needed.
- OSC 7 is gated behind `isProcessTrusted`, which returns `true` on macOS. Fine, but
  it's a silent failure mode if that ever changes.
- SwiftTerm 1.15 ships a Metal shader, so the build needs Xcode's **Metal toolchain**
  — a separate ~700 MB download (`xcodebuild -downloadComponent MetalToolchain`) that
  Xcode does not include. `Scripts/bootstrap.sh` detects it with `xcrun -f metal`
  (note: `xcodebuild -showComponent` returns 0 regardless and can't be used).

### Verification

- `HelmCore`: 11 tests. `HelmTerminal`: 8 tests. All pass in Swift 6 mode.
- Shell integration proven in a real PTY (via `script`): `cd /tmp` emitted a second
  OSC 7 with the new path; four commands emitted matching `133;C` starts and
  `D;0`/`D;1` finishes.
- Running app: app process spawns `/bin/zsh -l` as a child; typing `cd /Users` by
  hand updated the breadcrumb and folder list; the user's own themed prompt and
  colored `git status` output render correctly.

One test artifact worth remembering: feeding a heredoc into `script` without pacing
makes zsh consume all input before running per-command hooks, so only the initial
prompt's marks appear. It looks exactly like broken integration but isn't — pace the
input with `sleep` between commands.
